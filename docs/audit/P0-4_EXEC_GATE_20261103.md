## 1. 这一批要解决的问题

P0-3 之后，`run_command` 有两道边界：白名单（哪些命令允许跑）、argv 数组（不走 shell）。
但这两道只回答"**能不能**跑"，不回答"**谁批准了这一条**"。

具体后果：`git diff` 在白名单里，模型在一次对话里连续调用 20 次 `git diff` 和调用 1 次，
在控制面上没有区别。白名单是**能力边界**，不是**授权**。而"模型写的代码会被执行"这件事，
唯一真正的闸门就是执行前的授权。

本批新增 `src-tauri/src/perms.rs`：在 `run_allowed` 之前插一道 `gate_exec`，
把"允许执行"从"命中白名单"细化为"命中白名单 **且** 本次会话已授权"。

## 2. 实现要点

| 机制 | 位置 | 说明 |
|---|---|---|
| 三态判定 | `perms::decide` | `Deny`（不在白名单）/ `Ask`（在白名单但没批准）/ `Allow`（本会话已批准该 scope） |
| scope 粒度 | `perms::scope_of` | 命令 + 子命令：`["git","diff"]`、`["npm","run","build"]`。批一个不解锁另一个 |
| 授权存储 | `perms::Grant` | 只在进程内存，含 `uses_left: Option<u32>`；**不落盘**（落盘会把一次性批准变成永久后门） |
| 会话清理 | `ws_close` | 先 `perms::clear_session` 再 `wsx::close`，顺序不能反 |
| 唯一的受控入口 | `lib.rs:156` | 全仓只有一处 `crate::runx::run_allowed` 调用，且必须紧跟 `gate_exec`（有架构断言测试锁住） |
| 前端确认框 | `src/components/ConfirmExec.tsx` | 三选项：仅此一次 / 本工程目录都允许 / 拒绝；点遮罩等于拒绝 |
| 授权可见可撤 | `SettingsDrawer` | "已授予的执行权限"列表，逐条撤销 + 全部撤销 |

**为什么白名单外的命令不走 `Ask` 直接 `Deny`**：弹窗问一个本来就不该跑的命令，
只会训练用户无脑点同意；等真正危险的那条弹出来时，用户已经形成肌肉记忆。
`non_allowlisted_is_denied_not_asked` 是锁这条的单测。

**为什么删掉了 `run_decide`**：它实现为"查询当前会得到什么结论"，但内部走了
`decide()`——而 `decide()` 会扣 `uses_left`。也就是说一次"查询"会偷走一次授权。
删掉比改签名更安全：没有查询接口，就没有"查询带副作用"的可能。

### 3.1 P0-1 复现（npm 钩子）

```json
{ "scripts": { "pretest": "node evil.js", "test": "node --test emit.js" } }
```

`npm test` 的实测输出里有 `> p@1.0.0 pretest`，然后 `prehook-hit.txt` 被创建。
`test` 是受信任的 `node --test`，`pretest` 是任意脚本——只审 `scripts.test` 就放过了三步里的第 0 步。

修法：`check_npm_script` / `checkNpmCommandScript` 对 `pre<name>`、`post<name>` 一并审，
任一条不过整条命令拒绝。

### 3.2 P1-3 复现（`.npmrc` 改脚本 shell）

```
# .npmrc
script-shell=C:/nonexistent/zzz-shell.exe
```

`npm run build` → `npm error syscall spawn C:/nonexistent/zzz-shell.exe`。

**这里我先前判错过一次**：第一次测试用了不存在的脚本名，npm 在"脚本不存在"就退出了，
根本没走到 spawn，于是得到"没生效"的假阴性。换成"路径不存在但脚本存在"才暴露出来。
所以这条记的不只是缺陷，还有我第一次的错误结论。

`npm run build --script-shell=…` 和 `npm_config_script_shell=… npm run build` 在
npm 10.9.7 / Windows 上**没有**触发——但 `.npmrc` 触发了，说明机制是通的，
不能凭"某个入口没复现"就判它不存在。

修法：`.npmrc` / `.yarnrc` / `.yarnrc.yml` / `.pnpmfile.cjs` 归入 `is_toolchain_config`，
`fsx::write` 一律拒绝，与 `.git/**` 同级。

### 3.3 P0-2 驳回（8.3 短文件名）

复审主张：Windows 上 `.git` 可以写成 `GIT~1` 绕过首段比对。

本机实测（NTFS，`dir /x`）：`.git` 与 `.zxz` **没有** 8.3 短名；
`fs.statSync('GIT~1')` → `ENOENT`，`ZXZ~1` → `ENOENT`，`git~1` → `ENOENT`。
即本机不成立。`fs.statSync('.git')` 能拿到长名，说明路径本身是通的，不是测错了对象。

但我仍然加了一层：`write()` 在写入前对**父目录的 canonicalize 结果**再跑一次
`protected_area`（`parentc.strip_prefix(root)`）。理由是"本机没有短名"取决于卷的
8.3 生成策略，不是我能保证的前提。这是纵深防御，**不是**我承认这里存在可利用缺陷——
两者在报告里必须分开写。

### 3.4 P2-4 修法（撤销区读也关掉）

原设计只堵了写。但快照里留着用户删掉的密钥、改过的旧内容，**可读就是泄漏**；
能列举全量快照还额外泄漏操作轨迹（何时改过哪些文件）。

修法：`fsx::read` / `fsx::list_in` 对 `.zxz/undo` 直接拒绝；撤销面板改走
`undo_read` / `undo_list` 两条专用 IPC，只有面板调用，模型不可达。

## 4. 已知取舍（不修，说明理由）

| # | 项 | 为什么不修 |
|---|---|---|
| P3-7 | 一次性授权在闸门处扣，spawn 失败也扣 | 修它要把"扣额度"推迟到 spawn 成功之后，等于在安全关键路径上引入两阶段提交。失败方向是**更严**（要再批一次），不是更松——为省一次点击去改安全路径不划算 |
| P3-10 | `GIT_CONFIG_GLOBAL=<空设备>` 丢掉了用户的 `safe.directory` | 保留用户 gitconfig 就等于允许用户自己往里加 `textconv` / `fsmonitor`，那正是 DEC-003 要关掉的门。仓库属主不同导致 `dubious ownership` 时，报错是**明确**的，不是静默错误结果 |
| DEC-008 | 授权实际按工程目录记账，对话级靠前端撤回补偿 | 同一目录重复 `ws_open` 复用会话号，Rust 侧只有一个桶。真正按对话隔离需要让 `perms` 带 convId，那是新的会话维度，超出本批范围。已在 README 14.2.1 与 STATE.md DEC-008 写明这是补偿不是隔离 |
