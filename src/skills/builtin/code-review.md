# 代码审查

适用范围：review 别人的提交、review 模型刚写的代码、review 自己的旧代码。

## 硬规则

1. **先给结论再给细节**：一句话说这段代码能不能直接用（可以 / 修完可以 / 需要重写）。
2. **发现按严重度分三档**，不要平铺一堆：
   - **Blocking**：会导致错误行为、数据损坏、安全问题。必须改。
   - **Should fix**：可维护性、错误处理、性能隐患。建议改。
   - **Nit**：命名、排版、个人偏好。可忽略。
3. **每条都给四要素**：位置（文件:行号或函数名）、现象、为什么是问题（后果）、具体改法（代码）。
4. **不评价风格偏好**。缩进、引号、换行交给格式化工具；只在它掩盖真实问题时才提。
5. **区分事实与猜测**。没看到调用方就不要断言"这里一定空指针"，写成"如果 `user` 可能为 null，这里会崩"。
6. **优先看这五类真问题**：错误未处理、边界越界、并发/竞态、资源泄漏、安全（注入、越权、密钥硬编码）。
7. **给可执行的修改，不给"建议优化一下"**。要么写出替换代码，要么明确说明要补什么检查。
8. **没问题的部分也要说明看过**，否则用户不知道你是漏了还是确认过。
9. **不要顺手重写整个文件**。只改审查范围内的缺陷，保留原有结构与未提交的改动。

## 输出格式

```
结论：修完 2 处 Blocking 可以用。

Blocking
1. src/api.ts:42 未处理 fetch 失败 → 网络异常时静默返回 undefined，调用方会崩在 .data 上。
   改法：`if (!res.ok) throw new HttpError(res.status, ...)`

Should fix
2. src/store.ts:88 每次渲染都新建回调 → 子组件 memo 失效。
   改法：`const onPick = useCallback(..., [deps])`

Nit
3. src/store.ts:12 `d` 建议改名为 `deadline`。

已确认没问题：路径校验（三道）、撤销备份、错误回执。
```

## 自检清单

- [ ] 每条问题都能指出具体行/函数
- [ ] 每条都写了后果，而不是"不规范"
- [ ] 没有把偏好写成缺陷
- [ ] 给了改法，不只是诊断
- [ ] 明确列出检查过且没问题的范围

## 常见反例

- 「代码写得不太规范，建议优化命名和错误处理」——没有位置、没有后果、没有改法。
- 「这里应该加 try-catch」——不说明哪一行会抛什么、抛了以后怎么处理。
- 把 20 条 Nit 放在最前面，掩盖了 1 条会导致数据丢失的 Blocking。
