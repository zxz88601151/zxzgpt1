# 模块边界

核心一条：**接口窄、实现深。** 一个模块对外露出的东西越少，里面能改的余地越大。

判断标准很朴素：改一处内部实现，要不要动到调用方？要动，说明边界划错了。

## 四条硬规则

1. **接口窄**：对外只露必需的。能从参数推出来的不要暴露，内部状态不要暴露，临时字段不要暴露。
2. **依赖单向**：底层不知道上层存在。工具层不 import 业务层，业务层不 import 界面层。出现双向引用，说明一件事被劈成了两半。
3. **变更不外溢**：改一个模块的内部逻辑，其他文件的 diff 应该是 0 行。做不到，就是耦合。
4. **一个模块一个理由被改**：如果「改数据库」「改接口格式」「改界面文案」都会动到同一个文件，这个文件承担了太多。

## 怎么算「深」

深模块 = 接口很小，里面很多事。浅模块 = 接口很大，里面只是转发。

```
❌ 浅：8 个函数只是把参数透传给下层，调用方还得知道下层细节
   getUserById / getUserByEmail / getUserByName / saveUser / updateUser / ...

✅ 深：一个入口把该收的都收了，调用方不需要知道怎么查
   findUser({ id?, email?, name? }) → User | null
```

自检：删掉这个模块，把它的代码抄进调用方，会不会更简单？会，说明它没有提供真正的抽象。

## 依赖方向

```
界面 / 路由  →  业务逻辑  →  数据访问  →  外部
                                    ↘  纯工具（谁都可以用，它不依赖任何人）
```

- 箭头只能单向。反向调用用回调或事件，不要直接 import。
- 纯工具层（字符串、日期、格式化）不许 import 任何业务代码。
- 循环依赖不是「再抽一个文件」能解决的，通常是两个模块本该是一个，或者中间缺一层。

## 文件怎么切

- **按变化原因切，不按类型切。** 把「所有类型定义」放一个文件、「所有常量」放一个文件，是反模式——它们会因为完全不同的原因被改。
- 一个文件超过 300 行先看是不是混了两件事，而不是先想怎么拆。
- 目录层级不要超过三层。深目录通常意味着一层本该是命名空间。
- 公共代码被 2 处用到，先别抽；被 3 处用到，再抽。提前抽出来的「通用工具」多半长得不像任何真实用法。

## 接口签名纪律

- 参数超过 3 个，改成对象。顺序参数是最容易传错的东西。
- 布尔参数是坏味道：`save(data, true)` 读者不知道 `true` 是什么。用两个函数，或用选项对象。
- 返回值不要「有时是 null 有时抛异常」。选一种，写进约定，全程一致。
- 错误要带上下文：`找不到用户 42` 而不是 `not found`。
- 别把内部类型（数据库行、HTTP 响应）直接暴露成对外接口。中间差一层映射，改库的时候才知道值。

## 判断清单

动手写之前问一遍：

- [ ] 这个模块对外暴露了几个东西？能不能再少一个？
- [ ] 它 import 了谁？谁 import 它？有没有反向或循环？
- [ ] 里面换一种实现（换库、换算法、加缓存），调用方要不要改？
- [ ] 它只因为一个理由被改吗？
- [ ] 我要加的代码，是它本来该管的事吗？不是的话，该放哪？

## 反例

```ts
// ❌ 边界漏了：把数据库行直接当接口返回，调用方开始依赖 snake_case 字段
export async function getUser(id: string) {
  return db.query("select * from users where id = ?", [id]); // { user_name, created_at }
}
```

```ts
// ✅ 边界收住：外部只见 User，内部换表结构不影响调用方
export interface User { id: string; name: string; createdAt: number }

export async function getUser(id: string): Promise<User | null> {
  const row = await db.query("select * from users where id = ?", [id]);
  return row ? { id: row.id, name: row.user_name, createdAt: Number(row.created_at) } : null;
}
```
