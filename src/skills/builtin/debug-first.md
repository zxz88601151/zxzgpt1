# 先定位再修

核心一条：**没找到根因之前，任何改动都是猜。** 猜出来的修复会让代码里多出一层没用的防御，而真正的 bug 还在。

## 铁律

```
先回答「为什么错」，再动手改。
```

说不出「哪个文件、哪一行、在什么输入下、走哪条分支、哪一步开始偏离预期」，就还没到能改的阶段。

## 四个阶段

按顺序走，每一阶段结束前不要进下一阶段。

### 1. 把现象钉死

- 错误信息原文照抄，不要转述成「报了个错」。行号、字段名、状态码都有用。
- 能稳定复现吗？触发条件是什么：固定输入、特定顺序、只在某种数据下？
- 如果把条件改一个，还错吗？这一步是区分「逻辑错」和「环境错」最快的方法。
- 最近改过什么？先怀疑刚动过的地方，而不是先怀疑框架。

### 2. 假设与验证

- 写下**一个**具体假设：「因为 A 为空，所以 B 分支没进，导致 C 返回 undefined」。
- 这个假设要能被证伪：如果 A 不为空呢？如果 B 分支进了呢？
- 一次只验证一个假设。同时改三处再看到好了，你不知道是哪一处起的作用。
- 假设被推翻是好事，记下来，别回头再试一遍。

### 3. 定位到那一行

判断标准很硬：**能指出哪一行、能说出为什么这一行会错、能解释为什么之前看起来是对的。**

常见根因类别，按出现频率排：

| 类别 | 典型形状 |
| --- | --- |
| 边界没处理 | 空数组、`0`、`""`、`null` 走进了正常分支 |
| 时序 | 异步没 await、状态没刷新就读、事件在渲染前触发 |
| 作用域 | 闭包拿到旧值、`this` 不是以为的那个、变量被同名遮蔽 |
| 类型漂移 | 字符串 `"1"` 和数字 `1` 比较、可选字段被当成必有 |
| 状态残留 | 上一个用例/上一次请求留下的状态 |
| 假设错误 | 以为库会做某件事，实际它不做 |

### 4. 最小修复

- 只改根因那一处。顺手重构、顺手改格式、顺手加日志，都放到另一个改动里。
- 不为「也许以后会这样」加防御。防御层会掩盖真正的错误。
- 修完要能解释「为什么这个改动能消除现象」，而不是「改完好像好了」。
- 如果修完现象消失了但你说不出原因，那就是碰巧——要么没修好，要么修到了别的地方。

## 不准这样

- 加 `try/catch` 把错误吞掉，让现象消失。
- 加 `?.`、`|| 默认值` 把 `undefined` 变没，但没搞清它为什么是 `undefined`。
- 把条件放宽 / 收紧，试到不报错为止。
- 注释掉报错那一行。
- 一次改五处，然后说「修好了」。
- 看着像「同一类问题」就一起改。

## 输出约定

定位阶段的结论要写成四句话：

```
现象：<原文错误 / 具体表现>
根因：<文件:行> — <为什么会这样>
证据：<什么条件下必现，改成什么条件就不出现>
修复：<只改这一处，为什么这样能消除现象>
```

四句话缺任何一句，说明还没定位完，别进入修改。
